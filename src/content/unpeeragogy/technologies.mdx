### Claim

The node advocates for peer-driven technology selection where communities collectively evaluate and adopt tools based on shared needs rather than top-down mandates or vendor influence.

### Reality

A startup decides to build their community platform on Discord because "that's where developers hang out." Six months later, they're migrating to Slack because Discord's threading breaks their support workflows. Another six months, they're evaluating custom forums because Slack's search can't handle their knowledge base. The problem was never Discord, Slack, or forums.

Not the features. Not the integrations. Not the user experience.

The problem was assuming technology choice determines community success. Each migration burned weeks of developer time, fractured conversation history, and trained users that nothing here is permanent. Meanwhile, communities thriving on IRC from the 1990s ship code daily with tools that predate the web browser.

> What if the question isn't which technology to choose, but how much technology friction your community can honestly handle?

### Synthesis

These cases suggest that peer technology selection reveals governance capacity more than technical requirements. A community that can't decide between Slack and Discord probably can't handle the deeper conflicts that matter — who gets commit access, how to resolve design disagreements, what constitutes acceptable behavior.

The governance externalities run deeper than admin privileges. When one instance decides to defederate, users lose connections they built across that bridge. When formal review processes create bottlenecks, the real constraint becomes reviewer attention, not code quality. The technology shapes the social structure, but the social structure determines which technologies survive contact with actual use.

What remains to be tested is whether communities can resist the migration reflex — the assumption that better tools will solve social friction that better processes might address.
